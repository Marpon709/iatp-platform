# IATP 后端技术决策记录

## 001 在桥接层增加记录功能

原 Flask 引擎承担空间分析与路网计算，展示桥接层已有输入适配、缓存和任务状态。本版本在桥接层增加持久化，复用现有计算接口，减少对算法的侵入。

代价是保留两层服务，需要明确职责。原 Flask 接口被其他程序直接调用时，不会自动经过本版本的记录入口。后续若要统一，应抽出公共业务服务，而不是把记录逻辑复制到多个接口。

## 002 默认使用 SQLite 与 ORM

桌面展示需要完整解压后直接运行，SQLite 避免要求用户安装数据库服务。SQLAlchemy 负责表映射、查询和事务，Alembic 管理初始建表及后续结构升级。

每个数据库方法使用独立 Session，线程之间不共享 Session；写入在单桥接进程内串行化。SQLite 开启外键、WAL 和等待超时。这适合本地运行记录，但不意味着具备多实例部署或高写入吞吐。

数据库连接地址可以配置。当前只验收 SQLite，PostgreSQL/MySQL 的驱动、迁移和运行行为应另行验证。

## 003 保留记录并明确取消与重启语义

任务输入先落库，再启动计算；状态和结果随后保存。取消保留已完成的部分结果，数据库禁止终态被迟到状态覆盖。

服务重启把上次 running 标为 interrupted，保留已经保存的数据，不自动恢复计算。取消停止后续步骤，但无法撤回已经发给计算引擎的请求。用户重新提交时产生新编号，避免把历史记录持久化误写成断点续算。

首次记录失败时拒绝启动，避免产生无法追踪的新任务。任务已经执行后，临时写库失败通过 historyWarning 提示并允许后续重试，不把计算错误地改记为失败。

## 004 暂不增加并行 worker

原引擎的部分计算器、进度和结果包含共享可变状态，因此桥接层继续串行控制上游调用。线程让接口能及时返回，但没有消除计算器的共享状态。

后续若支持多用户并行，先把计算上下文、输出文件和任务状态按 jobId 隔离，再评估独立进程或外部队列。当前一个桥接服务对应一个运行数据库，不启动多个桥接进程共同管理同一组任务。

## 005 隔离应用运行数据

应用使用独立用户数据目录，凭据、缓存和运行记录不与其他应用混用。启动入口与应用名称统一为 IATP。

## 006 从真实结果生成一致性提示

新增 result_checks.py 在读取详情时检查路线汇总、坐标范围及活动空间返回结构，返回 validation 提示。校验不另加表，不修正原始 result，不给未实现的推荐校验制造通过状态。

路线总量和分段之和允许 0.15 的舍入差异，用于容纳已有显示精度。这个规则检查返回结果是否自洽，不能替代模型验证或证明真实出行时间、碳排系数正确。
